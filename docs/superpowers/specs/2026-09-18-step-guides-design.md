# 图文步骤教程站 · 设计稿

- 日期：2026-09-18
- 状态：已与用户逐项确认通过
- 仓库名：`Step-Guides`（GitHub Pages 发布）

## 1. 要解决的问题

用户教人（第一次是教女朋友设置 iPhone 专注模式）时，做了 12 张带红框标注的手机截图 + 对应文字，
只能在社交软件里「发一张图、发一段字」，体验割裂。做成 PDF/Word/Markdown 都嫌麻烦：
要配排版、要学语法、对方还要有能打开的软件。

**核心诉求**：写完随手发出一条链接，对方点开就能一步一步跟着做，尤其在手机上要看得清、不脱节。

### 1.1 这个项目最难的一处（先写在最前面）

素材是 iPhone 竖屏截图，实测 12 张的宽高比在 **1:2.04 ~ 1:2.22** 之间。
在 390px 宽的手机上按全宽显示，单张高度约 850px，**超过一整屏**——
图和它的说明文字在结构上不可能同屏出现。
如果只是把图文堆进一个网页，用户抱怨的「割裂」不会消失，只是换了个地方发生。

因此本项目的第一约束是：**一步 = 一屏**。

### 1.2 为什么不用现成轮子（2026-09-18 检索）

| 类别 | 代表项目 | 为什么不适用 |
|---|---|---|
| 自动录制型 | [westpoint-io/mimik](https://github.com/westpoint-io/mimik) 845★ | 只能录浏览器点击，抓不到 iPhone 屏幕 |
| 笔记/知识库 | [memos](https://github.com/usememos/memos) 63,150★、[AFFiNE](https://github.com/toeverything/AFFiNE) 72,741★、[outline](https://github.com/outline/outline) 40,607★、[docmost](https://github.com/docmost/docmost) 21,718★ | 要部署+账号；是通用文档，无步骤结构，未针对竖屏截图优化 |
| Markdown 粘贴板 | [mdbin](https://github.com/kevinfiol/mdbin) 20★ | 生态未成气候，且仍要写 Markdown |

借鉴的是 telegra.ph 的范式（不登录、贴图即用、发布得链接），但「步骤化 + 手机竖屏截图阅读」这层要自己做。

## 2. 已定型的决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 阅读版式 | **D 一步一屏左右翻页**为主，**A 长文流**可切换 | 四套真实视口对比图后用户选定；D 结构上杜绝图文分离，A 适合回看 |
| 托管 | GitHub 仓库 + Pages | 每教程约 0.3MB，1GB 上限可放三千多个；Vercel Hobby 额度按账号共享，已被其他项目占用 |
| 排除 Supabase | 是 | 免费项目闲置 1 周被暂停，发出去的链接会失效（supabase.com/pricing，2026-09-18） |
| 发布方式 | 网页内用 fine-grained PAT 直接提交 | 不碰命令行，手机上也能发 |
| 隐私 | 随机不可猜路径 + noindex + robots.txt | 免费方案下 Pages 站点必然公网可达（GitHub 官方文档），只能做到「猜不到、搜不到」 |
| 写作场景 | 电脑 + 手机都要能从头写 | 用户明确要求 |
| 内置标注工具 | **不做** | PixPin 已解决且更好用，不改变用户现有流程 |

### 2.1 已知限制（无法消除，只能兜住）

1. **Pages 每小时最多 10 次构建**（软限，GitHub 官方）→ 草稿只存本地，只有点「发布」才提交一次。
2. **手机发布依赖 `api.github.com` 可达性**，国内网络不稳定 → 失败不丢草稿、可重试、保留导出兜底。
3. **真机手感无法由本机自动化验证** → 交付时必须由用户在真机确认。

## 3. 架构

```
/w/            写作页（电脑 + 手机）
/t/<id>/       一个教程（id 为随机 8 位）
    index.html   壳子，引用公共阅读器
    data.json    标题 + 每步文字 + 图片清单（含原始宽高）
    i/01.webp…   压缩后的图片
/mine/         教程库列表（noindex，路径不公开）
/assets/
    reader.js / reader.css   阅读器（唯一一份）
    writer.js / writer.css   写作页
    github.js                Git Data API 封装
    img.js                   图片压缩
/list.json     教程索引
/robots.txt    Disallow: /
```

**为什么阅读器只有一份**：以后要调字号、改交互，改 `/assets/reader.js` 一处，所有历史教程一起生效，不必重新发布。
这是「死参数 vs 活参数」原则在文件结构上的应用。

## 4. 发布流程（关键技术选择）

用 **Git Data API** 而非 Contents API：

1. 每个文件 `POST /repos/{o}/{r}/git/blobs`（base64）
2. `POST /git/trees`（base于当前 HEAD tree）
3. `POST /git/commits`
4. `PATCH /git/refs/heads/main`

**理由**：Contents API 一次一个文件，12 张图要 14 次请求，中途失败会在仓库里留下半个教程。
Git Data API 的最后一步 ref 更新是原子的——要么整个教程上线，要么仓库完全没变。

发布后**轮询 `/t/<id>/data.json` 直到真的 200** 才报成功（Pages 构建有延迟；
参考日程卡片踩过的「推了但线上没更新」）。

token：fine-grained PAT，权限仅 `Contents: Read and write` 于本仓库，存 localStorage，可随时吊销。

## 5. 阅读页

- 默认 D 模式：`scroll-snap-type: x mandatory`，一屏一步；图 `flex:1` + `object-fit: contain`；文字块在下，最高 34vh，超出内部滚动
- 顶部：「第 n 步 / 共 N 步」+ 进度条
- 底部：「上一步 / 下一步」按钮，≥44px，位于拇指可达区
- 点图全屏放大，支持双指缩放
- 顶栏切换 A 模式（长文流），选择存 localStorage
- 深色模式下图片垫白底卡片（截图是浅色的，直接贴深色背景会晃眼）
- `data.json` 记录每张图原始宽高 → 阅读页预留位置，避免加载时跳动
- 最后一步显示完成态

## 6. 写作页

1. 选图：电脑拖拽 / `Ctrl+V` 粘贴；手机相册多选
2. 自动建步：N 张图 → N 个步骤位，按文件名排序
3. 排序：电脑拖拽；**手机改为「上移 / 下移 / 移到第几步」按钮**
   —— 全站唯一一处电脑与手机形态不同的地方。理由：多图拖拽在窄屏上落点难控，
   这是「确实做不好」的降级，不是省事（见移动端适配标准 §1.3 的例外条件）
4. 文字：纯文本框自动增高，不做富文本工具栏
5. 草稿：随敲随存 localStorage，发布失败不丢
6. 发布：压缩 → 一次提交 → 出链接 + 一键复制
7. 编辑已发布：`/w/?edit=<id>` 拉 data.json 回填，重新发布，链接不变

## 7. 图片处理

- **只在长边 > 1600px 时缩小，绝不放大**（用户的截图仅 412px 宽，放大或过度压缩都会糊）
- 转 WebP，质量 0.85，目标单图 ≤200KB
- 记录原始宽高写入 data.json

## 8. 明确不做

评论、账号体系、多人协作、富文本样式、视频、内置画框标注工具。

## 9. 验收标准

- [ ] 320 / 390 / 430 三档真实视口（headless Chrome + CDP，非注入 CSS）无横向溢出
- [ ] 阅读页 D 模式下，任意一步的图与其文字同屏可见
- [ ] 触摸目标 ≥44px 抽查通过
- [ ] 正文字号 ≥16px
- [ ] 发布中途断网：仓库不产生半个教程；草稿仍在
- [ ] 深浅两色模式各截图确认
- [ ] **真机确认（必须由用户完成）**：横滑跟手、双指放大、iOS 上底部按钮不被指示条挡住
